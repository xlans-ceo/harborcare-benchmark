## Product outcome and scope
Fictional Egyptian home-services business site. A visitor can understand the offer, browse active services, and submit a contact request. One demo administrator can sign in and manage service entries without editing code.

### Included
1. Arabic RTL, responsive public Home, Services, and Contact pages.
2. Contact form with server-side validation, understandable success/error states, and local database persistence; minimal fields: name, phone, optional service, message.
3. Demo admin login and service create/edit/delete workflow; minimal service fields: name, category, description, active status.
4. Real persistent SQLite database; server-side authentication, per-route authorization, validation, safe HTML output, parameterized SQL, and CSRF protection for admin mutations.
5. Automated functional, persistence, and negative authorization tests; meaningful invalid-input and unavailable/empty states.
6. Responsive, keyboard-usable UI designed with the already installed `ui-ux-pro-max` skill. Skill search/design only; no `--persist`, unverified writes, or additional skills.

### Excluded
Deployment/production readiness, real credentials or customer data, external integrations/email, payments, uploads, public user registration, viewing/processing contact inbox in admin, multi-role or multi-tenant features, prices, analytics, load testing, Git initialization, dependency/skill installation unless separately approved as genuinely necessary, global OpenCode/agent/model/provider/permission changes, and AgentOps.

## Approved technical direction
- Node.js v24 native modules: `node:http`, `node:sqlite`, `node:crypto`, and `node:test`; server-rendered semantic HTML and CSS. No third-party packages planned.
- Persistent SQLite file within `data/`; tests use isolated temporary DBs and ephemeral local ports.
- Native `scrypt` password hashing; opaque random session cookie (`HttpOnly`, `SameSite=Lax`) with only its hash persisted; CSRF token for state-changing admin requests; strict input/body limits; escaped output; prepared SQL statements.
- Demo account is fictional/local-only, clearly marked, and must never be represented as production-safe. No real secrets are needed.
- Trade-off: low setup/dependency burden and easy verification, versus hand-written HTTP/rendering code and `node:sqlite` experimental-status warning reported by Tech Lead. Local-only HTTP is not a production security boundary.

## Acceptance criteria
- **AC1 Public journey:** Home, Services, Contact return successfully in Arabic RTL and adapt to narrow and wide viewports; active services are sourced from SQLite; empty services render a useful empty state.
- **AC2 Contact:** valid submission is accepted and persisted once; invalid fields/body are rejected server-side without persistence; confirmation, validation, and generic server-error states are usable and do not expose internals.
- **AC3 Admin authentication:** valid demo login grants a session; invalid login grants none; logout/expiry invalidates access; session/password material is not stored in plaintext.
- **AC4 Service CMS:** authorized admin can create, edit, and delete a service; public services reflect active content; changes survive a server restart.
- **AC5 Authorization:** each protected read/mutation denies missing/invalid sessions; admin writes also reject missing/invalid CSRF; rejected operations leave DB unchanged. Tests cover these negative cases.
- **AC6 Safe handling:** server validates inputs and sizes, uses parameterized queries and context-safe escaping, and returns understandable errors without stack traces or secrets.
- **AC7 UX/accessibility:** responsive RTL layouts, labeled controls, keyboard access/focus, visible validation feedback, and usable touch targets. Actual browser visual verification is required if a working preview/browser is available; otherwise explicitly unverified.
- **AC8 Delivery evidence:** test/build commands and exit codes, DB persistence evidence, authorization evidence, UI skill usage, visual verification status, limitations, agent calls/retries, and observed usage metrics (or unavailable) are recorded. No claim of production readiness, security assurance, or load capacity.
